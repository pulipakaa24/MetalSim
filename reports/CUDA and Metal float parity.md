# Judge Metal parity against CUDA's own noise

metalsim should do both (c), but the two halves play different roles. **Statistical parity, judged against floors measured on the L4 itself, is the acceptance gate.** **Bitwise CUDA emulation is a scoped diagnostic tool.** Use it only where it is cheap and where it removes a discrete amplifier, and never make it a pass/fail requirement. The project's own measurements show why each half is needed. Adding one contraction pragma to the Warp fork's Metal path made Metal reproduce CUDA's FMA choices bit for bit on every simple pattern tested. After that change the a=2 column collapse tracks the L4 inside the L4's own float32 noise (28 nm vs 34 nm at frame 10; 165 vs 189 nm at 3 s), and the whole aspect-ratio suite passes. Cheap emulation therefore paid off, both as accuracy and as a bug detector: it exposed the watertight ray-triangle fallback bug. Full emulation is out of reach, though. NVIDIA's second contraction stage (ptxas) is undocumented, and under Warp's default PTX output it runs inside the *driver*. Isaac's own bits can therefore change with a driver update, and no published project has matched CUDA bitwise on another GPU vendor for a non-trivial simulation. The remaining Metal–CUDA gap in Newton's granular example comes from roughly 10 exact closest-face ties among 123k grid nodes. Those ties flip box-collider normals by up to 90°. Treat them as a measurable class of perturbation: build a CUDA-side "tie-sensitivity floor" by perturbing the L4 run in ways that themselves flip ties, and mirror ptxas's FFMA pattern in the one leaf routine that decides ties. Do not try to emulate the whole compiler.

## CUDA fuses in two stages, and the driver owns the second

On the CUDA side, contraction is decided twice. First, NVVM (NVRTC's closed LLVM fork) emits `fma.rn.f32` where its heuristic chooses. Upstream LLVM's NVPTX combine predicts its observed choices well. It handles FADD only, tries operand 0 first, then operand 1, and fuses a product only if the product has at most four users, all of them adds. So `a*b + c*d` becomes `fma(a,b,c*d)`, and `x*x+y*y+z*z` becomes `fma(z,z,fma(x,x,y*y))`. A multi-use product with a subtract user stays unfused ([NVPTXISelLowering.cpp](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/NVPTX/NVPTXISelLowering.cpp)). Second, every `mul`/`add`/`sub` left *without* `.rn` is fair game for ptxas. The PTX ISA says such sequences "may be optimized to use fused-multiply-add instructions on the target device", and that an explicit `.rn` is "treated conservatively" ([PTX ISA 9.4](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html)). Upstream LLVM emits `.rn` precisely to stop that ("prevents ptxas from creating FMAs") ([NVPTXInstrInfo.td](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/NVPTX/NVPTXInstrInfo.td)). NVVM under `--fmad=true` leaves plain ops behind, so ptxas makes the final call. **NVIDIA documents only the on/off switch for that stage, not its rules** ([nvcc docs](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)). The FFMA patterns found in `mesh_query_point`'s SASS, `u = fma(-vc, denom, 1-v)` and `c = fma(r, w, fma(p, u, q*v))`, include subtract fusions that the upstream FADD-only heuristic does not produce. They are most likely ptxas's work, and only disassembly can reveal them.

Two consequences matter for parity. First, the escape hatches are clean but change the reference. `fuse_fp=False` maps to `--fmad=false`, which yields all-`.rn`, fusion-free code except explicit `fmaf` calls, which always become FFMA ([NVIDIA forum, njuffa](https://forums.developer.nvidia.com/t/why-ffma-instructions-are-still-there-even-if-fmad-false-is-set/179934); [warp.cu v1.16.0](https://github.com/NVIDIA/warp/blob/v1.16.0/warp/native/warp.cu)). Isaac Lab does not run that way. Second, **Warp 1.16 emits PTX whenever the driver is at least as new as the toolkit, and loads it through the driver's JIT ptxas**. A driver upgrade on the same L4 can therefore move FFMA placement and change CUDA's bits; `wp.config.cuda_output = "cubin"` pins ptxas to the NVRTC toolkit ([context.py v1.16.0](https://github.com/NVIDIA/warp/blob/v1.16.0/warp/_src/context.py)). NVIDIA's own definition of determinism is conditional on "the version of the compiler and the Compiler Flags and Optimizations" and the same device ([CUDA Programming Guide §5.5](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/mathematical-functions.html)). In short, Isaac's reference is a function of (driver, toolkit, output format, fuse_fp, fast_math), and any reference metalsim records must store all five.

This framing also corrects one research note. The note speculated that float atomics in MPM's particle-to-grid scatter make Isaac nondeterministic. The project measured otherwise: **two L4 runs of the same scene were bitwise identical over 180 frames, and the granular example over 60**. GPUSimBench independently reports zero run-to-run spread for Isaac Lab ([GPUSimBench](https://huggingface.co/papers/2607.13059.md)). Run-to-run noise on CUDA is therefore zero, and any meaningful CUDA floor has to come from deliberate perturbations.

## Metal exposes contraction, but not rounding or denormals

Metal's spec makes contraction the default in every math mode. `fast` (the default) and `relaxed` set "FP contract to be fast", meaning fusion across statements, and **`safe` "sets the FP contract to on", meaning fusion only within a single statement** ([MSL Spec 4.1 §1.6.3](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)). Warp's generated code places each operation in its own SSA temporary, so no single statement ever contains both the multiply and the add. That explains why the fork's Metal path initially produced no fusion at all, and why `contract(fast)` was the switch that matched CUDA. The documented controls are `-ffp-contract=off`, `#pragma METAL fp contract(off|on|fast)` and `#pragma STDC FP_CONTRACT OFF`. `MTLCompileOptions` has `mathMode` and `mathFloatingPointFunctions` but no contraction property ([MTLCompileOptions](https://developer.apple.com/tutorials/data/documentation/metal/mtlcompileoptions.md)). For runtime-compiled source, a pragma is therefore the only lever. The fork currently uses the clang spelling (`#pragma clang fp contract(fast)`). It works, but **switching to the documented `#pragma METAL fp contract(fast)` and re-running the bitwise FMA probes is a cheap hardening step**.

What Metal does not expose is the bigger risk. The spec permits fp32 denormals to "be flushed to zero" and allows either round-to-nearest-even or round-toward-zero. An Apple DTS engineer confirmed in September 2026 that no API selects or queries either one, and that "selecting safe math is not sufficient on its own" to stop contraction ([Apple Developer Forums 844598](https://developer.apple.com/forums/thread/844598)). Reverse-engineered documentation of the M1-generation (G13) ISA models fp32 sources and destinations as flush-to-zero, while fp16 is not flushed ([applegpu docs](https://dougallj.github.io/applegpu/docs.html)). The project's bitwise matches on `a*b+c`, sums of squares and the other patterns show empirically that the M4 Max rounds to nearest-even for normal operands. Denormals were never exercised. Because Apple treats strict IEEE behaviour as unsupported by contract, both properties have to be probed on each GPU family and macOS version and re-probed after OS updates. For bit-sensitive work, the baseline Metal configuration is `mathMode = .safe`, `mathFloatingPointFunctions = .precise` and an explicit contract pragma. The default `fast` mode allows reassociation, and the spec warns it "may dramatically change results" ([MSL Spec 4.1 §8.4](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)).

## Nobody matches CUDA bitwise across vendors; simulators gate on tolerance

Every engine that claims cross-platform bitwise determinism follows the same CPU-only recipe: contraction off, no fast-math, in-house transcendentals, every ordering fixed, and CI hash checks. Box2D v3 disables contraction with `-ffp-contract=off` and replaces `atan2f` because it differed across platforms ([Box2D blog](https://box2d.org/posts/2024/08/determinism/)). Jolt's cross-platform mode costs about 8% and its docs call it "less tested" ([Jolt docs](https://jrouwe.github.io/JoltPhysics/index.html)). Rapier pins transcendentals to a pure-Rust libm ([Rapier](https://rapier.rs/docs/user_guides/rust/determinism/)). None of them attempts GPU determinism. GPU vendors scope their guarantees to the same toolkit, architecture and SM count (cuBLAS) or the same product name (oneMKL CNR) ([cuBLAS §2.1.4](https://docs.nvidia.com/cuda/cublas/index.html#results-reproducibility); [Intel CNR](https://www.intel.com/content/www/us/en/developer/archive/training/conditional-numerical-reproducibility-cnr.html)). Warp 1.15's `GPU_TO_GPU` mode fixes the reduction order in thread-index order to aim for consistency across NVIDIA architectures. It does not address contraction ([Warp deterministic execution](https://raw.githubusercontent.com/NVIDIA/warp/main/docs/user_guide/execution_and_performance/deterministic_execution.rst)). These engines all win the same way: they *own both sides* and forbid optional fusion everywhere. metalsim owns only the Metal side. It cannot recompile Isaac's reference with contraction off and still call that run Isaac.

Multi-backend robotics simulators therefore gate on tolerance, not bits. MuJoCo Warp checks state against MuJoCo C with `atol = rtol = 5e-4`, a "mostly due to float precision" tolerance inflated tenfold "to avoid test noise" ([mujoco_warp forward_test.py](https://raw.githubusercontent.com/google-deepmind/mujoco_warp/main/mujoco_warp/_src/forward_test.py)). MJX uses 1e-4 ([mjx forward_test.py](https://raw.githubusercontent.com/google-deepmind/mujoco/main/mjx/mujoco/mjx/_src/forward_test.py)). Newton's own implicit-MPM tests compare sparse topology and values bitwise between code paths *on one device*, use rtol/atol of 2e-6 to 3e-5 for physics quantities, and use invariant checks for the flow rule ([test_implicit_mpm.py](https://raw.githubusercontent.com/newton-physics/newton/main/newton/tests/test_implicit_mpm.py)). Isaac Lab states outright that solver families are "not numerically portable" and validates PhysX against Newton through policy transfer ([Isaac Lab physics backends](https://isaac-sim.github.io/IsaacLab/v3.0.0-EA/source/concepts/physics_backends.html)). For chaotic many-body systems the literature compares ensembles and macroscopic observables, not trajectories: DEM round-robins ([Dosta et al. 2024](https://eprints.ncl.ac.uk/295860)), MD uncertainty quantification ([Wan, Sinclair & Coveney 2021](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC8059622/)), and GPUSimBench's Earth Mover's Distance. Shadowing theory explains why. A numerical orbit stays near *some* true orbit for tens of Lyapunov times, but local errors reach O(1) against a specific reference orbit within about 9 ([Hayes, astro-ph/0209508](https://arxiv.org/pdf/astro-ph/0209508)).

## Newton's box collider turns last-bit differences into 90° normals

The granular divergence is not ordinary rounding growth. It is a discrete event. Newton 1.5.2's implicit MPM tessellates every primitive collider, including boxes (12 triangles), into a `wp.Mesh`, even though Newton ships an analytic `sdf_box_grad` ([implicit_mpm_model.py v1.5.2](https://github.com/newton-physics/newton/blob/v1.5.2/newton/_src/solvers/implicit_mpm/implicit_mpm_model.py)). Each grid node calls `mesh_query_point_no_sign`, which keeps a triangle only if `dist_sq < min_dist_sq` (strict), so on an exact tie the first-visited triangle wins ([Warp mesh.h v1.17.0](https://github.com/NVIDIA/warp/blob/v1.17.0/warp/native/mesh.h)). Outside a convex box this is harmless, because every tied face yields the same closest point. **Inside the box, on a medial plane, the tied faces yield different closest points.** The node normal `normalize(x − cp)·sign` then becomes the outward normal of whichever face won, and at a box edge the two candidates differ by 90°. With `n = +z` a sinking node loses its normal velocity and gets friction. With `n = +x`, `u·n = 0`, so `solve_coulomb_isotropic` does nothing and the node keeps sinking ([rasterized_collisions.py v1.5.2](https://github.com/newton-physics/newton/blob/v1.5.2/newton/_src/solvers/implicit_mpm/rasterized_collisions.py); [contact_solver_kernels.py v1.5.2](https://github.com/newton-physics/newton/blob/v1.5.2/newton/_src/solvers/implicit_mpm/contact_solver_kernels.py)). The winning face also selects the material index and the velocity sample point. Axis-aligned boxes whose centres and half-extents are multiples of the voxel size put whole rows of nodes exactly on these planes.

The project has already removed both structural causes. LBVH was ported to Metal, so traversal order is identical; Warp's default is SAH on the CPU and LBVH on CUDA ([types.py v1.17.0](https://github.com/NVIDIA/warp/blob/v1.17.0/warp/_src/types.py)). Barycentrics at the tied faces are now bit-identical on both devices. What remains is purely arithmetic: the inline distance is computed with different FFMA placement, for example SASS's `dist = fma(dz,dz,fma(dx,dx,dy*dy))`. So two faces that tie exactly on one device are strictly ordered on the other. **About 10 of 123k nodes flip, one particle moves 3 cm after frame 1, and the trajectory reaches 0.24 mm RMS by frame 6, against a 0.05 µm CUDA floor at that frame.** The established remedies all leave Newton's semantics: angle-weighted pseudonormals at shared features ([Bærentzen & Aanæs 2005](https://orbit.dtu.dk/en/publications/signed-distance-computation-using-the-angle-weighted-pseudo-norma/)), an explicit tie-break such as smallest face index within a tolerance band, analytic primitive SDFs, or Newton's experimental `collider_normal_from_sdf_gradient`. None of the surveyed libraries defines a canonical normal on the interior medial axis; libigl also keeps the first-visited face under a strict `<` ([libigl AABB.cpp](https://raw.githubusercontent.com/libigl/libigl/main/include/igl/AABB.cpp)). For *Isaac parity* the only faithful fix is to reproduce CUDA's arithmetic in that one routine. For *metalsim's own physics*, a deterministic tie-break is simply better engineering and worth proposing upstream, since no Newton or Warp issue on ties exists yet.

## Recommendation: both, with statistics as the gate

Reject (a) as a gate. Bitwise CUDA emulation would mean reverse-engineering undocumented ptxas fusion from SASS per kernel, porting libdevice transcendentals, and reproducing CUDA's approximate division and square root in Newton's `fast_math` kernels. All of that would be re-done whenever NVIDIA ships a driver, because Warp's default PTX path lets the driver re-decide FFMA placement. A gate that a driver update on the reference machine can break is a gate on the wrong thing. (b) alone is also insufficient: without arithmetic alignment, Metal's divergence would sit near the outer edge of CUDA's floors everywhere, and a real porting bug would hide inside the noise. The project's history shows the payoff of alignment. Once contraction matched, a 28 nm vs 34 nm comparison became meaningful, and the ray-triangle fallback bug stood out.

So adopt (c), split by role. **Bitwise emulation is a scoped instrument:** keep the global `contract(fast)` pragma, keep LBVH, and mirror the SASS FFMA pattern with explicit `fma()` under a local `contract(off)` scope in exactly the tie-deciding leaf (`closest_point_to_triangle` and the `dist_sq` computation in the Metal fork's `mesh_query_point_core`). Extract the pattern with `nvdisasm` from a **cubin** build, so it reflects the pinned toolkit's ptxas and not the driver's ([CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)). Success means the selected face index is equal at all 123k nodes in frame 0. Stop emulating when a site needs more than a few lines, or when it involves transcendentals or `fast_math` approximations. **Statistical parity is the acceptance gate:** Metal passes if its divergence from the L4 stays inside an envelope built from CUDA-vs-CUDA perturbations, including perturbations that flip ties. The reference itself must be pinned. Record the L4 references with `cuda_output="cubin"` and store the driver, toolkit, Warp commit, `fuse_fp` and `fast_math` with every run. Then re-record one canonical scene after any driver change and log the CUDA-vs-CUDA delta as a new floor entry.

There is real uncertainty. Mirroring one leaf routine may not eliminate every flip, because near-ties can also be decided in `distance_to_aabb_sq` during traversal, or in `get_average_face_normal`'s summation order. The tie-sensitivity floor below is what keeps the gate honest whatever the mirroring achieves.

## What this means for the metalsim parity suite

Every floor is measured on the L4, at the same frames, with the same scene and observables as the Metal comparison. Define three floors. **F_arith(t)** is the maximum over the CUDA arithmetic perturbations: float64 vs float32 accumulation, `fast_math` on vs off, and `fuse_fp` True vs False *in a tie-free scene variant*. Measured values for the granular scene are about 5e-8 m at frame 6 and about 0.6 mm RMS by 1 s (max 5 cm). **F_tie(t)** is the envelope of CUDA runs perturbed in ways that flip closest-face ties in the tie-dense scene: `fuse_fp=False`, cubin vs PTX output (toolkit vs driver ptxas), the SAH vs LBVH `bvh_constructor` on CUDA, and a 1-ulp shift of the collider pose. For each perturbation, record the number of flipped collider normals per frame alongside the trajectory RMS; a perturbation that flips no ties does not count toward F_tie. **F_seed** is the spread across the ≥10 jitter seeds already used for the statistical tier. CUDA run-to-run divergence is measured as zero, so it is a determinism check, not a floor.

| Tier | What is compared | Pass criterion |
|---|---|---|
| T0 Determinism | Metal vs Metal, CUDA vs CUDA, same build | Bitwise-identical particle state over the full horizon |
| T0 Arithmetic conformance | Probe kernels on both devices: `a*b+c`, `a*b±c*d`, 3-term sums, sums of squares, `(a-b)*(c-d)+e`, `c-a*b`, multi-use products, plus the SASS-mirrored `mesh_query_point` leaf; sqrt/div in non-fast-math modules | Bitwise equal; re-run after every macOS, Xcode, driver or toolkit change |
| T0 Discrete structure | BVH topology, sparse matrix topology, active-node sets, closest-face index at non-tie nodes, and tie-node face index once mirrored | Bitwise equal; report the tie-node mismatch count separately |
| T1a Arithmetic trajectory | Tie-free scenes (column collapse; granular scene with the box offset by a non-dyadic amount), frames 1 to N | Metal–L4 RMS(t) ≤ 2·F_arith(t) at every frame. Currently met: 28 vs 34 nm at frame 10, 165 vs 189 nm at 3 s |
| T1b Tie-sensitive trajectory | Tie-dense scenes (Newton granular example), frames 1 to 60 | Metal flip count ≤ max CUDA-perturbation flip count, and Metal–L4 RMS(t) ≤ F_tie(t) at every frame. If F_tie(6) is far below 0.24 mm, the Metal flips are a Metal-specific defect: fix them by mirroring, not by loosening the tolerance |
| T1c Divergence growth | log RMS(t) slope, Metal–L4 vs CUDA–CUDA perturbed | Metal slope no steeper than the steepest CUDA perturbation slope, within fit error |
| T2 Statistical | Column collapse sweep, repose, silo, RFT, granular end state over ≥10 seeds | Seed means within the combined 2σ of F_seed (currently 0.1–0.4%), and fitted scaling exponents equal within fit error (currently equal to 3 decimals) |
| T3 Task | Replayed-action robot scenes | Task observables within the CUDA seed and perturbation spread |

**Denormal flushing must be tested, not assumed.** Write a Metal probe that stores raw bits for: subnormal inputs such as 2^-130 and the smallest subnormal passed through add, mul, fma, sqrt and division; products of two normals that underflow into the subnormal range; and a plain load-store round trip, to separate arithmetic flushing from memory flushing. Run it under both `safe` and `fast` modes, on each Apple GPU generation used. If the M4 Max flushes, the next question is whether any of it matters. Instrument the L4 reference to count nonzero values below 1.17549435e-38 in grid velocities, stresses, impulses and SDF values per frame. If the count is zero, flushing is moot and should be documented as such. If it is nonzero, bound its effect by re-running the L4 with FTZ, by passing `--ftz=true` through a two-line NVRTC-options patch in a CUDA-side Warp build, and add that run to F_arith. Note that Newton's `fast_math` kernels already flush on CUDA, because `--use_fast_math` implies `--ftz=true` ([NVIDIA forum](https://forums.developer.nvidia.com/t/how-does-use-fast-math-affect-division-precision-in-cuda/355548)), so those kernels are already matched in that respect. Store the probe outputs in the reference metadata so that a future macOS change that alters flushing shows up as a T0 failure, not as unexplained T1 drift.

## Conclusion

The parity question has changed from "how close is Metal to CUDA" to "is Metal's divergence the same *kind* as CUDA's own". Smooth arithmetic noise and discrete tie events grow at different rates and need different floors. A single tolerance would either hide the tie flips or reject the arithmetic noise. Once the flips are explained, the useful observation is that 0.24 mm at frame 6 is far outside CUDA's arithmetic floor yet possibly inside its tie floor. Only the F_tie measurement can tell whether metalsim has a bug or has merely found Newton's sensitivity first.

The deeper implication is that Isaac's reference is less fixed than it looks. It is bitwise reproducible run-to-run, but only for a fixed driver, a fixed output format and tie-free luck in its collider geometry. Newton's tessellated box collider is a tie generator that turns 1-ulp differences into 90° normals on *any* backend, CUDA included. Running the CUDA-side perturbation campaign therefore pays twice: it sets metalsim's tolerances, and it produces a concrete, reproducible upstream report for Newton showing that collider-normal tie handling is a portability hazard.
