## Q1. What do the literature and mature libraries do when a point is equidistant from several triangles?

### Takeaway
None of the libraries I checked break exact distance ties by an explicit rule; each keeps the first triangle its BVH traversal reaches. libigl and Warp both use a strict `<`. The literature's answer is not to pick a triangle at all. It classifies the closest *feature* (face, edge or vertex) and uses that feature's normal. For an edge or vertex that is the angle-weighted pseudonormal (Bærentzen & Aanæs 2005), which is the same whichever incident triangle the search returned. This removes ties when the closest *point* is shared, for example outside a convex box near an edge. It does **not** remove ties when two different faces give different closest points at equal distance. That is the medial-axis case inside a solid, for example on the internal bisector plane of a box edge. There the distance field is not differentiable, and no library I found defines a canonical normal.

### Cited Findings
- Bærentzen & Aanæs, "Signed Distance Computation using the Angle Weighted Pseudonormal", IEEE TVCG 11(3):243–253, 2005, DOI 10.1109/TVCG.2005.49. At mesh vertices and edges the surface is not C1, so the normal is undefined there. The angle-weighted pseudonormal (Thürmer & Wüthrich; Séquin) correctly separates inside from outside whether the closest feature is a vertex, an edge or a face. The sign therefore comes out of the distance computation itself. Earlier versions: a 2002 IMM tech report and VMV 2003 "Pseudo-Normals for Signed Distance Computation". — [DTU Orbit record](https://orbit.dtu.dk/en/publications/signed-distance-computation-using-the-angle-weighted-pseudo-norma/); [PDF](https://backend.orbit.dtu.dk/ws/portalfiles/portal/3977815/B_rentzen.pdf); [VMV 2003 record](https://orbit.dtu.dk/en/publications/pseudo-normals-for-signed-distance-computation/)
- **libigl, closest-face selection**: `AABB::set_min` updates the best candidate only if `sqr_d_candidate < sqr_d` (strict). There is no tie-break by index, so on an exact tie the primitive visited first in the traversal wins. — [libigl AABB.cpp](https://raw.githubusercontent.com/libigl/libigl/main/include/igl/AABB.cpp)
- **libigl, feature classification** (`pseudonormal_test`): it computes barycentric coordinates of the closest point `c` on face `f` with `epsilon = 1e-12`. It counts coordinates `<= epsilon`. If two are near zero it uses the vertex normal `VN`. If one is near zero it uses the edge normal `EN` for the opposite edge (via `EMAP`). Otherwise it uses the face normal `FN`. Degenerate triangles (area ≤ `MIN_DOUBLE_AREA = 1e-4`) use distance tests instead. Sign is `s = (q-c)·n >= 0 ? +1 : -1`, so an exact zero counts as outside. — [libigl pseudonormal_test.cpp](https://raw.githubusercontent.com/libigl/libigl/main/include/igl/pseudonormal_test.cpp)
- libigl `signed_distance` offers a pseudonormal path (`tree.squared_distance(...)` then `pseudonormal_test`) and a winding-number path. `SIGNED_DISTANCE_TYPE_DEFAULT` falls through to the winding number (`s = 1 - 2*w`). libigl cites Bærentzen & Aanæs for its fast pseudonormal sign test. — [libigl signed_distance.cpp](https://raw.githubusercontent.com/libigl/libigl/main/include/igl/signed_distance.cpp); [libigl signed_distance.h mirror](https://git.inf-cv.uni-jena.de/3DFaces/libigl_Martin/src/master/include/igl/signed_distance.h)
- **Open3D RaycastingScene**: `compute_closest_points` returns `points`, `geometry_ids`, `primitive_ids` (closest triangle), `primitive_uvs` and `primitive_normals`, where the normal is the *normal of the closest triangle*, not a feature pseudonormal. `compute_signed_distance` gets the sign by counting ray intersections with `nsamples` rays (odd, default 1). The docs warn that rays hitting edges or vertices can flip the sign. The docs say nothing about closest-point ties. — [Open3D RaycastingScene docs](https://www.open3d.org/docs/release/python_api/open3d.t.geometry.RaycastingScene.html)
- **Warp**: in issue #922, a user reported inconsistent signs and artifacts from `mesh_query_point`, `mesh_query_point_sign_normal` and `mesh_query_point_sign_winding_number` compared with Open3D. Warp added `mesh_query_point_sign_parity` (ray parity, released in v1.11), and the reporter confirmed it matched Open3D to about 1e-4. PR #1117 changed `mesh_query_point` to parity counting with multi-sample perturbed-ray majority voting, "to avoid edge cases (rays hitting exactly on edges/vertices)". These changes address the *sign*, not which closest face is chosen. — [warp#922](https://github.com/NVIDIA/warp/issues/922); [warp#938](https://github.com/NVIDIA/warp/issues/938); [warp#1117](https://github.com/NVIDIA/warp/pull/1117)
- **Warp `mesh_query_point_sign_normal`** comes closest to the literature. It collects every face within `min_dist + epsilon_min_dist` of the closest distance, where `epsilon_min_dist = mesh.average_edge_length * epsilon` and `epsilon` defaults to 1e-3. It accumulates `weight * normalize(normal)`, with `weight` set to the triangle's corner angle (`acosf(dot(...))`) when the closest point is within epsilon of a vertex. In other words, it computes an angle-weighted pseudonormal with a tolerance band instead of an exact feature test. — local source `upstream/warp-innate/warp/native/mesh.h` lines ~487–600 (function `mesh_query_point_sign_normal`); [Warp repo](https://github.com/NVIDIA/warp/blob/main/warp/native/mesh.h)
- **PhysX SDF mesh collision** stores a dense or sparse sampled SDF (subgrid resolution, narrow band, 8/16/32-bit samples). Normals come from the sampled field, not from closest-triangle selection. The docs do not describe how gradients are computed. — [PhysxSDFMeshCollisionAPI](https://docs.omniverse.nvidia.com/kit/docs/omni_usd_schema_physics/latest/class_physx_schema_physx_s_d_f_mesh_collision_a_p_i.html); [Omni Physics collision guide](https://docs.omniverse.nvidia.com/kit/docs/omni_physics/108.0/dev_guide/guides/collision_guide.html)

### Inferences
- With strict `<` and no index tie-break, the triangle returned at an exact tie depends on traversal order, and so on BVH topology. Near a tie it also depends on last-bit rounding in each triangle's `closest_point_to_triangle` (which `dist_sq` is smaller by 1 ulp). The usual robust remedy has three parts:
  1. Classify the closest feature with a tolerance and use the feature's pseudonormal, which is identical for every incident triangle.
  2. Where several *distinct* closest points lie within a tolerance band (the medial axis), either average their normals or break the tie deterministically, for example by smallest face index or by a fixed axis priority.
  3. Better still, avoid the question with analytic primitive SDFs or a smoothed SDF gradient (see Q2).
- The Ericson-style closest-point-on-triangle routine (vertex, edge and face Voronoi regions tested with `<=`/`>=` on dot products) is what Warp uses (`closest_point_to_triangle` in `warp/native/intersect.h`). Its region tests are themselves boundary cases, but they produce the same closest *point* on both sides of a region boundary, so they do not cause normal flips.

- I could not reach the full text of Ericson's *Real-Time Collision Detection* §5.1.5 for a direct quote.

## Q2. Do MPM / grid codes use analytic SDFs for primitive colliders?

### Takeaway
Practice varies. Simple MPM codes (Taichi examples) use analytic, axis-aligned wall conditions applied per velocity component, so they have no normal-selection problem. Genesis evaluates per-geometry SDF and normal functions at grid nodes. Newton's implicit MPM is the exception: it **tessellates every primitive (box, sphere, capsule, cylinder, cone, plane) into a triangle mesh** and queries Warp's closest-point BVH, even though Newton ships analytic `sdf_box`/`sdf_box_grad` functions for other solvers.

### Cited Findings
- Taichi `mpm3d.py`: boundaries are analytic grid walls, with `cond = (I < bound) & (v < 0) | (I > n_grid - bound) & (v > 0); v = select(cond, 0, v)`. They act per component with `bound = 3`, so this is a slip wall with no normal computation. — [taichi mpm3d.py](https://raw.githubusercontent.com/taichi-dev/taichi/master/python/taichi/examples/simulation/mpm3d.py)
- Genesis legacy coupler: at each MPM grid node, `_func_collide_with_rigid_geom` calls `sdf.sdf_func_world(...)` and `sdf.sdf_func_normal_world(...)` for each coupled rigid geometry. Influence is `min(exp(-d/coup_softness), 1)` and coupling applies only when influence > 0.1. The excerpt did not show whether primitives use analytic or precomputed-grid SDFs. — [Genesis legacy_coupler.py](https://raw.githubusercontent.com/Genesis-Embodied-AI/Genesis/main/genesis/engine/couplers/legacy_coupler.py); [Genesis coupling docs](https://genesis-world.readthedocs.io/en/latest/user_guide/theory/solvers_and_coupling.html)
- Newton 1.5.2 `_get_shape_mesh` (in `implicit_mpm_model.py`) maps `GeoType.BOX` to `newton.Mesh.create_box(hx, hy, hz, duplicate_vertices=False, ...)`. PLANE becomes `create_plane` (1000×1000 if "infinite"), and SPHERE, CAPSULE, CYLINDER and CONE also become meshes. `_create_body_collider_mesh` merges all collision shapes of a body into **one** `wp.Mesh(points, indices, zeros)`. — [implicit_mpm_model.py @ v1.5.2](https://github.com/newton-physics/newton/blob/v1.5.2/newton/_src/solvers/implicit_mpm/implicit_mpm_model.py) (lines ~89–170, ~217–240)
- `create_mesh_box` (in `newton/_src/utils/mesh.py`) splits each box face into **two triangles** (12 triangles in total). A box edge or vertex is therefore shared by a varying number of triangles from each adjacent face (1 or 2, depending on the diagonal). — [utils/mesh.py @ v1.5.2](https://github.com/newton-physics/newton/blob/v1.5.2/newton/_src/utils/mesh.py) (line ~1962)
- Newton's analytic `sdf_box_grad` (`geometry/kernels.py:237`) returns `normalize(p - clamp(p))` for exterior points. Inside the box it returns the axis of the largest `q_i = |p_i| - h_i`, using **strict** `>` comparisons and a fallback to z. It is not used by implicit MPM. — [geometry/kernels.py @ v1.5.2](https://github.com/newton-physics/newton/blob/v1.5.2/newton/_src/geometry/kernels.py)

### Inferences
- Analytic box SDF: outside the box the gradient is well defined everywhere, pointing toward the clamped point, which is the edge or vertex direction in edge and vertex regions. Inside, the gradient is discontinuous on the medial planes, the same mathematical tie as with a mesh. The difference is that the analytic version breaks the tie by a deterministic, platform-independent rule (axis priority) instead of BVH order and rounding.
- Caveat in Newton's `sdf_box_grad`: from my reading of the code, for an interior point with `qx == qy > qz` (equidistant from an x face and a y face) neither the x branch nor the y branch fires. The function falls through and returns `(0, 0, sign(z))`, the direction of the *farthest* face. It is deterministic but geometrically wrong on that bisector. I did not execute it; this is a code reading.

### Gaps
- I did not verify whether Genesis's `sdf_func_normal_world` is analytic for boxes or comes from a precomputed grid, or whether Warp's own MPM examples use analytic colliders.
- I did not look at Hu et al. MLS-MPM / CPIC rigid coupling for tie handling.

## Q3. How exactly does Newton 1.5.2 SolverImplicitMPM compute collider SDF and normals at grid nodes, and does it handle ties?

### Takeaway
Each grid node calls `wp.mesh_query_point_no_sign`, which returns one face. The node then takes `cp = mesh_eval_position(face, u, v)`. The sign comes from an "average face normal": the unweighted sum of the normals of all triangles within 1e-3 of `cp`. The node normal is `normalize(x - cp) * sign` when `|d| >= 1e-3`, and the average face normal otherwise. There is no tie handling. Outside a convex collider this works without trouble, because every tied face gives the same `cp`. **Inside** a collider on a medial plane (for example a node equidistant from a box's top and side faces), the face that wins in Warp's BVH traversal decides the normal. The two candidates differ by 90° for a box edge. Across colliders, `collision_sdf` also uses strict `<`, so the lower stable collider index wins exact ties.

### Cited Findings (all from [rasterized_collisions.py @ v1.5.2](https://github.com/newton-physics/newton/blob/v1.5.2/newton/_src/solvers/implicit_mpm/rasterized_collisions.py), line numbers from the local v1.5.2 checkout)
- Constants: `_CLOSEST_POINT_NORMAL_EPSILON = 1.0e-3` (absolute, in metres in the collider's local frame), `_SDF_SIGN_FROM_AVERAGE_NORMAL = True`, `_COLLIDER_ACTIVATION_DISTANCE = 0.5` voxels (lines 20–32).
- `_query_collider_sdf` (lines 177–235):
  - transforms the node into the body frame (`quat_rotate_inv`);
  - `max_dist = query_max_dist + thickness`;
  - `query = wp.mesh_query_point_no_sign(mesh, x_local, max_dist)` because `_SDF_SIGN_FROM_AVERAGE_NORMAL` is True (the alternative path is `wp.mesh_query_point`, ray-parity sign);
  - `cp = wp.mesh_eval_position(mesh, query.face, query.u, query.v)`;
  - `face_normal = get_average_face_normal(mesh, cp)`; `sign = dot(face_normal, x_local - cp) > 0 ? 1 : -1` (exact zero gives -1, i.e. inside);
  - the material is taken from `face_material_index[... + query.face]`, so the chosen face also selects the material, and thus friction and thickness;
  - `d = |x_local - cp| * sign`; `sdf = d - material_thickness`;
  - `sdf_grad = face_normal` if `|d| < 1e-3`, else `normalize(x_local - cp) * sign`;
  - velocity comes from `mesh_eval_velocity(face, u, v)`.
- `get_average_face_normal` (lines 140–173): runs `wp.mesh_query_aabb(mesh, cp ± 1e-3)`; for each overlapping triangle, if the squared point-triangle distance is below `(1e-3)^2` it adds `mesh_eval_face_normal` (unit face normal, **not angle-weighted**). It returns `normalize(sum)`.
- `collision_sdf` (lines 238–315): loops over the colliders of the node's world in stable order and keeps a result only if `query_result and sdf < min_sdf` (strict). The chosen `sdf_grad` is then rotated to world and re-normalized.
- `rasterize_collider_kernel` (lines 429–505): a node is active if `sdf < 0.5 * voxel_size`. It writes `collider_normals[i] = sdf_gradient` together with friction, adhesion (scaled by `dt * node_volume / voxel_size`) and velocity.
- Optional smoothing: `SolverImplicitMPM.Config.collider_normal_from_sdf_gradient: bool = False` ("experimental", docstring "Compute collider normals from sdf gradient rather than closest point"). When enabled, `interpolate_collider_normals` replaces the node normals with the normalized FEM gradient of the rasterized distance field (`collider_gradient_field`, lines 626–667). Values larger than `min_sdf + |Δx|` are replaced by a linearization based on the min-node normal. — [solver_implicit_mpm.py @ v1.5.2](https://github.com/newton-physics/newton/blob/v1.5.2/newton/_src/solvers/implicit_mpm/solver_implicit_mpm.py) (lines ~893, 2695–2701)
- The same `mesh_query_point_no_sign` face choice also sets the barycentric coupling weights for deformable colliders in `fill_collider_coupling_matrices` (lines ~566–600).
- The contact solve uses the normal through `solve_coulomb_isotropic(mu, n, u)`. With `u_n = u·n`, if `u_n < 0` it removes the normal component and then either sticks (`|u_t|^2 <= (mu*u_n)^2` gives `u = 0`) or scales the tangential part by `1 + mu*u_n/|u_t|`. If `u_n >= 0` it does nothing. Warm-starting projects the stored impulse onto the friction cone around `n` (`filter_collider_impulse_warmstart`). — [contact_solver_kernels.py @ v1.5.2](https://github.com/newton-physics/newton/blob/v1.5.2/newton/_src/solvers/implicit_mpm/contact_solver_kernels.py) (lines 64–98, 125–170)
- `project_outside_collider` (optional particle-level pass) uses the same `collision_sdf` gradient to remove normal velocity and push particles out along `sdf_gradient` by `min(0, sdf_end + ...)`. — rasterized_collisions.py lines 347–426

Related MPM PRs exist, for example #1108 "Subgrid collisions for mpm solver" and #4294 "Fix deformable MPM collider barycentric weights", but neither concerns ties. — [newton#1108](https://github.com/newton-physics/newton/pull/1108); [newton#4294](https://github.com/newton-physics/newton/pull/4294)

### Inferences
- **Exterior nodes (convex box):** the closest point is unique (on a face, edge or vertex). Every tied triangle returns the same `cp` up to rounding, so `normalize(x - cp)` is the same whichever face wins, and the normal is well defined. One subtlety: `mesh_eval_position` evaluates `cp` from (face, u, v), so different faces can give `cp` values differing in the last bits. This only perturbs the normal at the ulp level.
- **Near-surface nodes (|d| < 1e-3):** the normal is the unweighted average of the normals of triangles within 1e-3 of `cp`. With the two-triangle box tessellation, an edge `cp` can collect 1 triangle from one face and 2 from the other. That biases the "edge normal" (for example toward atan(2/1) ≈ 63° rather than 45°). This is exactly the tessellation dependence that angle weighting (Bærentzen & Aanæs) removes. The *set* of faces is deterministic, so the only device dependence is summation order inside the AABB-query traversal, an ulp-level effect.
- **Interior nodes on a medial plane** (penetrating nodes equidistant from two faces): the two candidate closest points differ, each face's average normal is just that face's normal, and the result is `sdf_grad = -(x - cp)/|x - cp|`, the outward normal of whichever face won. The candidates differ by 90° at a box edge (and three axes are possible near a corner). The winner is decided first by which `dist_sq` is smaller in float32 after `closest_point_to_triangle`, then on exact equality by Warp's traversal order (Q4). Effect on the solve:
  - suppose the normals are `+z` and `+x` and the node moves along `-z`;
  - with `n = +z`, `u_n < 0`, so normal velocity is removed and friction applies;
  - with `n = +x`, `u_n = 0`, so `solve_coulomb_isotropic` does nothing and the node keeps sinking. The tangential/normal split for friction also changes completely;
  - `project_outside_collider` would push the particle out through a different face; both exits are minimal-distance on a tie.
  - The SDF *value* is identical either way. Only the normal, the material/face index and the velocity sample point differ.
- **Ties between colliders** (two bodies equidistant) are resolved deterministically by the lower collider index, because of the strict `<` in the stable-order loop.
- `collider_normal_from_sdf_gradient=True` gives an FEM-gradient normal that depends only on the nodal SDF values, which are tie-invariant. It would remove most of the face-choice dependence for nodes whose element has valid values. The `min_grad` fallback still uses the face-chosen normal of the minimum node.

### Gaps
- I found no Newton documentation explaining why `_SDF_SIGN_FROM_AVERAGE_NORMAL` is unweighted, or whether ties were considered.
- I did not measure how often grid nodes fall exactly on box medial planes in practice. That is likely for axis-aligned boxes whose centres and half-extents are multiples of the voxel size.

## Q4. How does Warp's mesh_query_point pick the closest face, and are there reported device-dependent tie results?

### Takeaway
All `mesh_query_point*` variants (except `sign_normal` and `furthest`) run a nearest-child-first BVH descent and accept a triangle only if `dist_sq < min_dist_sq` (strict). So on an exact tie the **first-visited** triangle wins. Visit order depends on BVH topology, and Warp builds the BVH with **SAH on CPU and LBVH on CUDA by default**. The same mesh can therefore return different tied faces on CPU and GPU, and a third backend such as Metal may differ again. Child distances that tie go to the right child. I found no Warp or Newton issue reporting tie nondeterminism.

### Cited Findings
- Warp 1.17.0 `mesh_query_point_no_sign` (`warp/native/mesh.h` ~line 502) works like this:
  - it pops a stack and re-tests `node_dist_sq > min_dist_sq`, culling a node only if it is strictly farther;
  - at a leaf it skips slivers (`|n| / Σ|e|^2 < 1e-6`), computes `closest_point_to_triangle(p, q, r, point)` and `c = u*p + v*q + w*r`, and updates only on `if (dist_sq < min_dist_sq)`;
  - at an internal node it pushes the far child, then the near child (if `left_dist_sq < right_dist_sq` the left child is near; otherwise, including ties, the right child is near). Each is pushed only if `child_dist < min_dist_sq`.
  — [Warp v1.17.0 mesh.h](https://github.com/NVIDIA/warp/blob/v1.17.0/warp/native/mesh.h)
- In later Warp (issue #1844, fixed by commit f005e09), the four variants were refactored into one shared `mesh_query_point_core` ("shrinking-radius" traversal with child distances carried on the stack), described as a "pure refactor; distances bitwise-identical". The local 1.18 dev copy keeps `if (dist_sq < min_dist_sq)` and "visit the nearer child first (ties go right)", with a far child dropped if the stack is full. — [warp#1844](https://github.com/NVIDIA/warp/issues/1844); local `upstream/warp-innate/warp/native/mesh.h` lines ~128–275
- Default BVH constructor in `wp.Mesh.__init__`: `if bvh_constructor is None: SAH if device.is_cpu else LBVH`. LBVH on CPU falls back to SAH with a warning. Options are "sah", "median", "lbvh" and "cubql". Newton's MPM collider uses `wp.Mesh(collider_points, collider_indices, zeros)` with no `bvh_constructor`, so it gets the device default. — Warp 1.17.0 `warp/_src/types.py` lines ~6096–6184 ([source](https://github.com/NVIDIA/warp/blob/v1.17.0/warp/_src/types.py)); [implicit_mpm_model.py @ v1.5.2](https://github.com/newton-physics/newton/blob/v1.5.2/newton/_src/solvers/implicit_mpm/implicit_mpm_model.py)
- Warp's `closest_point_to_triangle` (`warp/native/intersect.h` line 44) is the region-classification closest-point routine: vertex regions `d1<=0 && d2<=0`, `d3>=0 && d4<=d3`, edge regions `vc<=0 && d1>=0 && d3<=0`, and so on. — [Warp intersect.h](https://github.com/NVIDIA/warp/blob/v1.17.0/warp/native/intersect.h)
- Searching GitHub issues and PRs in NVIDIA/warp for "mesh_query_point" found only sign-robustness work (#922, #938, #1117), cuBQL backend support (#1467) and the traversal refactor (#1844). Nothing about ties or device-dependent face selection. — [warp#1467](https://github.com/NVIDIA/warp/issues/1467)

### Inferences
- Determinism on a single device holds as long as the BVH is built identically. LBVH (Morton-code sort on GPU) and SAH give different topologies, and so different first-visited faces at exact ties. Near-ties are decided by float32 rounding of `closest_point_to_triangle`, `distance_to_aabb_sq` and `length_sq`, which can differ under FMA contraction across compilers (see the sibling note `cuda_fma_contraction.md`). Those differences alone can flip which of two tied faces is "strictly smaller".
- To match CUDA bit for bit on another backend, the options are:
  - (a) reproduce the LBVH build and the traversal order exactly, plus the same FMA behaviour; or
  - (b) make the result tie-invariant: an explicit tie-break (for example, among faces with `dist_sq <= min + tol`, choose the smallest face index or a canonical axis), or a feature/pseudonormal or analytic-primitive normal.

  Option (b) changes results relative to stock Newton on the medial-plane nodes, so it would then no longer match Newton's output exactly.

### Gaps
- I did not check whether Warp's LBVH build is itself deterministic across GPU runs (for example, Morton-code sort stability with duplicate codes). The 12-triangle box with coincident centroid codes is a plausible duplicate-key case.
- I did not test how the cuBQL backend orders tied faces.
