# Apple Metal shader compiler floating-point semantics (FMA contraction, math modes) and bit-for-bit parity with CUDA

Research date: 2026-10-10. Primary source is the current Metal Shading Language Specification PDF, downloaded from Apple and text-searched locally. It identifies itself as **Version 4.1, dated 2026-06-04**, so it is newer than MSL 3.1/3.2. The text quoted below is from that version, but the options it describes are introduced as "In Xcode 16 and later ... (SDK supporting iOS 18 or macOS 15)", which is the MSL 3.2 era. Spec page numbers refer to the 383-page 4.1 PDF.

## Q1. What does the MSL spec say about math modes, contraction, pragmas, fma and the precise:: / fast:: namespaces? Does safe mode allow contraction by default?

### Takeaway
Yes, safe mode allows contraction. The spec says `safe` "sets the FP contract to on", and the default mode (`fast`, and also `relaxed`) sets contract to **fast**. "On" means fusion only within a single statement, and "fast" means fusion across statements. The documented controls are `-ffp-contract=off`, `#pragma METAL fp contract(off|on|fast)`, `#pragma STDC FP_CONTRACT OFF` and `#pragma METAL fp math_mode(relaxed|safe|fast)`. There is no API to select the arithmetic rounding mode or how denormals are handled, and the spec explicitly permits both RTZ rounding and flush-to-zero.

### Cited Findings
- **Spec version and date:** the current PDF is "Metal Shading Language Specification, Version 4.1", with page footers reading "2026-06-04 | Copyright © 2026 Apple Inc." — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **§1.6.3 "Math Intrinsics Compiler Options" (p.15)** lists the fast-math optimizations: No NaNs, No INFs, No Signed Zeroes, Allow Reciprocal, Allow Reassociation, and "**Allow Contract: Allow floating-point contraction across statements.** For example, allow fusing a multiple followed by an additional into a single fused-multiply-add." — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **§1.6.3 version note:** "In Xcode 16 and later and Metal Developer Tools, Metal supports the following options for Windows 5 (SDK supporting iOS 18 or macOS 15)". The options are:
  - `-fmetal-math-fp32-functions=<fast|precise>`: "sets the single-precision floating-point math functions described in section 6.6 to call either the fast or precise version. **The default is fast.** For Apple silicon, starting with Apple GPU Family 4, the math functions honor INF and NaN."
  - `-fmetal-math-mode=<fast, relaxed, safe>`: "**The default is fast.**"
  — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **§1.6.3, what each mode means for contraction (pp.15–16), verbatim:**
  - fast: "lets the compiler make aggressive, potentially lossy assumptions about floating-point math. These include no NaNs, no INFs, no signed zeros, allow reciprocal, allow reassociation, and **FP contract to be fast**."
  - relaxed: "...but honors INFs and NaNs. These include no signed zeros, allow reciprocal, allow reassociation, and **FP contract to be fast**. This supports Apple silicon."
  - safe: "disables unsafe floating-point optimizations by preventing the compiler from making any transformations that might affect the results. **This sets the FP contract to on.**"
  — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **Legacy flags (p.16):** "-ffast-math: Equivalent to -fmetal-math-fp32-functions=fast and -fmetal-math-mode=fast." and "-fno-fast-math: Equivalent to -fmetal-math-fp32-functions=precise and -fmetal-math-mode=safe." — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **Fast-math assumptions (p.16):** "the use of fast math asserts that the shader will never generate INF or NaN. If the program has an expression X/Y, the compiler can assume Y is never zero ... If Y can be zero, you would have an undefined program if compiled with fast math." — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **Math-mode pragma (p.16):** "The #pragma metal fp pragmas allow you to specify floating-point options for a source code section. ... It can only appear in file or namespace scope, within a language linkage specification, or at the start of a compound statement (excluding comments). When using it within a compound statement, the pragma is active within the scope of the compound statement: `#pragma METAL fp math_mode([relaxed | safe | fast])`" — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **Contraction controls (pp.16–17), verbatim:** "By default, the compiler allows floating-point contractions. For example, a*b+c may be converted to a single fused-multiply-add. These contractions could lead to computation differences if other expressions are not contracted. To disable allowing the compiler to contractions, pass the following option: `-ffp-contract=off`. The compiler also supports controlling contractions with the following pragma: `#pragma METAL fp contract([off | on | fast])`. Using off disables contractions, **on allows contractions with statement, and fast allows contractions across statements.** You can also use: `#pragma STDC FP_CONTRACT OFF`" — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **New in MSL 4.1 (p.17):** "In Metal 4.1 and later, use the following option to change the default rounding mode for float-to-float conversions from RTNE (round to nearest, ties to even) to RTZ (round toward zero) for compatibility with non-Metal APIs: `-fmetal-rtz-fp-conversion`" — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **`fma` definition (§6.5 math functions table):** "T fma(T a, T b, T c) Returns the correctly rounded floating-point representation of the sum of c with the infinitely precise product of a and b. Rounding of intermediate products shall not occur. Edge case behavior is per the IEEE 754-2008..." — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **precise:: / fast:: namespaces (§6.5, p.208–209):** "For single precision floating-point, Metal supports two variants for most of the math functions listed in Table 6.4: the precise and the fast variants. ... The ffast-math compiler option ... selects the appropriate variant ... In addition, the metal::precise and metal::fast nested namespaces provide an explicit way to select the fast or precise variant". The example is `float b = fast::sin(x); float c = precise::cos(x);`. The same mechanism applies to `clamp` and `saturate` (§6.3, where the variants differ only in NaN handling) and to `distance`, `length` and `normalize` (§6.9). — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **§8.1 denormals:** "Denormalized single-precision, half-precision, or brain floating-point numbers passed as input to or produced as the output of single-precision, half-precision, or brain floating-point arithmetic operations **may be flushed to zero**." — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **§8.2 rounding:** "Either round ties to even or round toward zero rounding mode may be supported for single-precision, half-precision, and brain floating-point operations." **§8.3:** "Floating-point exceptions are disabled in Metal." — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **§8.4 accuracy tables:** Table 8.1 (precise) lists x+y, x−y, x*y, 1.0/x, x/y, sqrt, rsqrt, fma, floor, ceil, rint, round, trunc, fract, ldexp and fdim as "Correctly rounded". Transcendentals have ULP bounds, for example sin ≤4 ulp, tan ≤6 ulp, tanh ≤5 ulp. Table 8.2 (fast math, "which is the default unless you specify -fno-fast-math") keeps + − * correctly rounded but gives "1.0 / x <= 0.6 ulp" and "x / y <= 0.6 ulp" for y in [2^-126, 2^126]. — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **§8.4 caveat:** "the Metal compiler, in fast math mode ..., may do various optimization like reassociate floating-point operations that may dramatically change results ... and thus cannot be in code that relies on rounding behavior such as (x + 2^52) - 2^52, or ordered floating-point comparisons." — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **§8.6 conversions:** float→int uses RTZ, and NaN→int gives 0. float→half and float→bfloat use RTNE. — [MSL Spec PDF](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- **MTLCompileOptions API:** properties include `mathMode: MTLMathMode`, `mathFloatingPointFunctions: MTLMathFloatingPointFunctions` ("The FP32 math functions Metal uses"), the legacy `fastMathEnabled: Bool`, `floatingPointConversionRoundingMode`, `preprocessorMacros`, `languageVersion` and `optimizationLevel`. **The documented property list has no contraction or `-ffp-contract` property and no generic "extra compiler flags" property.** — [Apple: MTLCompileOptions](https://developer.apple.com/tutorials/data/documentation/metal/mtlcompileoptions.md)
- **MTLMathMode case descriptions:** safe: "disable unsafe floating-point optimizations by preventing the compiler from making any transformations that could affect the results". relaxed: "aggressive, potentially lossy assumptions about floating-point math, while honoring Inf/NaN". fast: "aggressive, potentially lossy assumptions about floating-point math". The `fast` page notes it is the default for Intel and AMD devices. — [Apple: MTLMathMode](https://developer.apple.com/tutorials/data/documentation/metal/mtlmathmode.md), [Apple: MTLMathMode.fast](https://developer.apple.com/documentation/metal/mtlmathmode/fast.md)
- **Apple DTS answer (Apple Developer Forums, Sep 2026), accepted:** "No API selects or queries the FP32 arithmetic rounding mode, and none controls or queries denormal handling. I checked the Metal framework headers in both the current and the upcoming SDK. There is no denormal-related declaration of any kind, and the only rounding controls present are for conversions and for texture writes." On contraction: "Section 1.6.3 documents one compiler option and two pragmas that disable contraction ... **Selecting safe math is not sufficient on its own.** The same section says of safe mode that it 'sets the FP contract to on'." DTS also says `floatingPointConversionRoundingMode` covers narrowing conversions only and "is annotated for macOS 27 and iOS 27". The Metal Feature Set Tables "contain no rounding entries". — [Apple Developer Forums thread 844598](https://developer.apple.com/forums/thread/844598)
- **The same thread lists related cross-API efforts to get strict-FP32 controls:** SPIR-V issue #448, HLSL specs issue #926 and WebGPU issue #2259. — [Apple Developer Forums thread 844598](https://developer.apple.com/forums/thread/844598)

### Inferences
- **Why safe mode with no pragma did not fuse `a*b+c` in our backend:** the spec defines contract "on" as "allows contractions with[in a] statement". Warp-style generated code emits one operation per SSA temporary (`var_3 = wp::mul(a,b); var_4 = wp::add(var_3,c);`), often through helper function calls, so no single source statement contains both the multiply and the add, and "on" never applies. `contract(fast)` permits fusion across statements, which matches the observed behaviour. This is consistent with clang semantics (Q2), where "on"-mode fusion is decided by the front end per expression, before inlining.
- **The empirical `#pragma clang fp contract(fast)` working is consistent with the documented `#pragma METAL fp contract(fast)`.** The Metal front end is clang-based. The documented, Apple-supported spelling is `#pragma METAL fp contract(fast)`, and it would be safer to switch to it or at least test it.
- **When generating source at runtime, MTLCompileOptions cannot set contraction.** It only exposes mathMode and mathFloatingPointFunctions. Contraction therefore has to come from pragmas in the generated source, or from offline `xcrun metal -ffp-contract=...` compilation into a metallib.
- **A bit-exact baseline therefore needs:** `mathMode = .safe` (no reassociation, NaN/Inf/signed-zero preserved), `mathFloatingPointFunctions = .precise`, and an explicit contract pragma. Even then, Apple only permits, and does not guarantee, RTNE and denormal preservation (see Q2 for the hardware FTZ evidence).
- **Calls are never bit-identical in general.** Transcendentals (sin, exp, tanh and so on) have ULP bounds, not correct rounding, on both Metal and CUDA, and the two libraries use different implementations. Bitwise parity requires porting CUDA's libdevice algorithms into MSL, built only from correctly-rounded primitives and explicit `fma`.

### Gaps
- I could not obtain the MSL 3.1 or 3.2 PDFs (Apple serves only the current 4.1). It is unverified whether the 3.2-era text said exactly the same about "safe sets FP contract to on". The Xcode 16 / macOS 15 framing suggests the options date from then.
- The spec does not say whether `#pragma METAL fp contract(...)` overrides the contract setting implied by `MTLMathMode`, or the reverse. Our empirical result (safe mode plus a fast pragma fuses) suggests the pragma wins.
- The spec does not document `[[clang::...]]` FP attributes for Metal. I found no source on whether `__attribute__((optnone))` or `[[clang::optnone]]`-style blocking works in MSL.

## Q2. Is Apple's GPU backend LLVM-like (aggressive FMA fusion)? What does the toolchain expose (AIR, flags), and can contraction be inspected?

### Takeaway
The Metal front end follows clang/LLVM floating-point semantics: the same `-ffp-contract` values and pragma vocabulary, with "on" meaning within a statement and "fast" meaning across statements. The reverse-engineered Apple G13 ISA has native fp32 and fp16 `fmadd`. It models fp32 operands and results as flush-to-zero, unlike fp16, which matters for CUDA parity when CUDA keeps denormals. I found no public Apple documentation of the backend fusion heuristics. Inspection is possible only through offline AIR output or reverse-engineered disassemblers.

### Cited Findings
- **Clang `-ffp-contract` semantics (Metal mirrors this vocabulary):** `fast` "enable fusion across statements disregarding pragmas" (the default for CUDA). `on` "enable C and C++ standard compliant fusion in the same statement unless dictated by pragmas" (the default for languages other than CUDA/HIP). `off` disables fusion. `fast-honor-pragmas` "fuse across statements unless dictated by pragmas" (the default for HIP). The manual says "pragmas will be ignored with -ffp-contract=fast" and that fusion "can be controlled with the FP_CONTRACT and clang fp contract pragmas". — [Clang Users Manual](https://clang.llvm.org/docs/UsersManual.html)
- **Inconsistency in the clang manual itself:** the `-fno-fast-math` section says it sets `-ffp-contract` to `on` ("`fast` for CUDA and HIP"), which conflicts with the HIP default `fast-honor-pragmas` given elsewhere on the page. — [Clang Users Manual](https://clang.llvm.org/docs/UsersManual.html)
- **There was an LLVM RFC on making `-ffp-contract=fast` honour pragmas**, showing that pragma-versus-flag precedence is a known, version-dependent area in clang. — [LLVM Discourse RFC: Honor pragmas with -ffp-contract=fast](https://discourse.llvm.org/t/rfc-honor-pragmas-with-ffp-contract-fast/80797/14)
- **Apple G13 (M1) ISA, reverse engineered by dougallj:** lists `fmadd` ("Floating-Point Fused Multiply-Add", `result = fused_multiply_add(a, b, c)`) and `fmadd16` (half precision). `fadd` is modelled as `fused_multiply_add(a, 1.0, b)` and `fmul` as `fused_multiply_add(a, b, 0.0)`. — [dougallj applegpu docs](https://dougallj.github.io/applegpu/docs.html)
- **applegpu denormal model:** 32-bit destinations use `RoundToFloat32Wrapper(destination, flush_to_zero=True)` and 32-bit sources use `Float32ToRealWrapper(source, flush_to_zero=True)`. 16-bit sources and destinations use `flush_to_zero=False`. The docs specify no arithmetic rounding mode, have no round-to-zero modifiers on ALU ops (only abs and negate source modifiers), cover only G13 (M1), and warn the doc "is likely to have mistakes". — [dougallj applegpu docs](https://dougallj.github.io/applegpu/docs.html)
- **Apple confirms no control over FTZ or rounding exists**, and that the spec only permits flushing and RTZ. — [Apple Developer Forums thread 844598](https://developer.apple.com/forums/thread/844598)
- **Local check:** on this machine (macOS Darwin 25.6), `xcrun -f metal` returns "unable to find utility 'metal'". The offline Metal compiler is not installed here, so I could not produce AIR or `-S -emit-llvm` output to inspect contraction. (Observed directly in this session; no URL.)

### Inferences
- **The Metal front end almost certainly uses clang's mechanism.** It emits `llvm.fmuladd` for within-statement contraction under "on" and sets the `contract` fast-math flag on fmul/fadd under "fast", leaving the backend to fuse. Fusion across statements under "fast" is then a backend decision, presumably DAG-combine-style and usually per basic block, governed by the target's "FMA is faster" hooks. This is inferred from the shared flag vocabulary. Apple does not document its backend.
- **Likely reasons for the remaining differences inside large inlined functions:**
  1. **Which product gets fused.** For `a*b + c*d`, one compiler may emit `fma(a,b,c*d)` and another `fma(c,d,a*b)`, and the two give different bits. NVIDIA's own guidance notes this ambiguity. — [NVIDIA forum: FMA precision issue](https://forums.developer.nvidia.com/t/fma-precision-issue/19858)
  2. **Where fusion happens.** NVCC/NVRTC can fuse at both the NVVM and ptxas level, after inlining and its own scheduling, while an LLVM-style backend fuses per DAG or basic block. Fusion opportunities across control flow (select or branch merges) can therefore differ.
  3. **Reassociation or algebraic simplification** if anything other than `safe` is used.
  4. **fp32 denormal flushing** on Apple hardware versus CUDA's default IEEE denormals when fast-math/ftz is off.
  5. **Different library implementations** for divide (if not precise), sqrt approximations and transcendentals.
- **The most robust parity strategy is to stop relying on implicit contraction on the Metal side.** Use `#pragma METAL fp contract(off)` plus `safe`/`precise`, and have the Warp-to-MSL code generator emit explicit `fma(a,b,c)` exactly where CUDA's SASS contains FFMA (found by dumping CUDA SASS with `cuobjdump -sass` or `nvdisasm` for the reference kernels). Explicit `fma()` is correctly rounded per §6.5/§8.4 and immune to contraction heuristics. Matching ptxas fusion decisions in general, however, means replicating its choices, which only SASS inspection can reveal.
- **Inspecting the Metal side** would require installing the Metal toolchain (`xcrun metal -S -emit-llvm` to read AIR fmul/fadd flags and `llvm.fma` / `llvm.fmuladd` calls). Native GPU code could be checked with applegpu's disassembler, but it targets G13/M1, and M4 (a later generation) encodings may differ.

### Gaps
- No public Apple documentation of the AGX backend's FMA fusion heuristics, of AIR's representation of contraction flags, or of an official GPU-ISA disassembler.
- I did not verify how to install the offline Metal toolchain on Xcode 26 (my recollection is that it became a separately downloaded component, but I found no source), nor whether `metal-objdump` exposes AIR.
- I did not fetch the Asahi Linux AGX compiler docs or Mesa source. Whether Asahi's compiler fuses fmul+fadd, and how its fp32 denormal handling and rounding compare across G13, G14 and G16 (M4-era), remains open. applegpu covers only G13.
- I did not verify Warp's NVRTC defaults for `--fmad` (CUDA's own default is fmad=true unless disabled).

## Q3. WWDC sessions and Apple forum posts on FP precision, FMA, reproducibility and Metal vs CUDA

### Takeaway
The only authoritative Apple statement I found is the September 2026 DTS forum answer: safe math alone does not disable contraction; arithmetic rounding (RTNE vs RTZ) and FP32 denormal behaviour can be neither selected nor queried; requests go to Feedback Assistant. I found no WWDC session on FMA contraction or cross-API reproducibility.

### Cited Findings
- **The forum question asked for a "queryable strict FP32 configuration"** of safe math, precise FP32 functions, contraction disabled, RTNE arithmetic, preserved denormals, and defined signed-zero/Inf/NaN, for "deterministic GPU numerical simulation". DTS confirmed that only the contraction part is controllable today, and suggested filing documentation and enhancement requests. — [Apple Developer Forums thread 844598](https://developer.apple.com/forums/thread/844598)
- **The OP's summary, which DTS's answer supports:** "safe mode sets FP contraction to on, so applications requiring separate rounding points must additionally use -ffp-contract=off or an equivalent pragma"; "arithmetic may use either round-to-nearest-ties-to-even or round-toward-zero"; "denormal inputs and results may be flushed independently of the selected math mode". — [Apple Developer Forums thread 844598](https://developer.apple.com/forums/thread/844598)

### Inferences
- **Apple treats strict IEEE reproducibility as unsupported by contract.** Current hardware behaviour has to be established empirically with probes on each GPU family, OS and compiler, and re-validated after OS updates.

### Gaps
- I did not find WWDC sessions on Metal floating-point precision or FMA. Searches returned nothing relevant, and I did not review transcripts session by session, so this may be a search miss rather than absence.

## Q4. Known cross-API numerical differences when porting CUDA kernels to Metal (PyTorch MPS, MLX, llama.cpp, Taichi/Genesis) and how projects handled FMA and fast-math

### Takeaway
Projects that need Metal test parity disable fast math. llama.cpp found that `setFastMathEnabled:false` "seems to have no effect" for them and builds the metallib offline with `-fno-fast-math`. MLX users hit the fast-by-default `exp` and work around it with `metal::precise::`. I found no project documenting a solution for bit-exact FMA contraction parity with CUDA.

### Cited Findings
- **llama.cpp (ggml), commit "metal : switch back to default.metallib (ggml/681)" by ggerganov.** CMake comments: "# note: this is the only way I found to disable fast-math in Metal. it's ugly, but at least it works", "# disabling fast math is needed in order to pass tests/test-backend-ops", "# note: adding -fno-inline fixes the tests when using MTL_SHADER_VALIDATION=1", and `set(XC_FLAGS -fno-fast-math -fno-inline -g)`. In ggml-metal.m: "// try to disable fast-math // NOTE: this seems to have no effect whatsoever // instead, in order to disable fast-math, we have to build default.metallib from the command line" with `//[options setFastMathEnabled:false];` commented out. The commit date was not shown; it is from roughly early 2024 based on the ggml PR number, which is unverified. — [llama.cpp commit 91d3887](https://github.com/ggml-org/llama.cpp/commit/91d38876dfa10332359ac671b62353aeceb448d3)
- **MLX issue #3592 ("Add support for compiler options" to `mx.fast.metal_kernel`).** The API cannot pass Metal compiler flags. Bare `exp()` resolves to `metal::fast::exp`, which "may not handle exp(-INFINITY) = 0.0 correctly". The workaround is explicit `metal::precise::exp`. The proposed fix is `compile_options` such as `-fmetal-math-mode=relaxed` or a math_mode enum. (Seen via a GitHub mirror, not the original page.) — [MLX issue #3592 (mirror)](https://upd.dev/ml-explore/mlx/issues/3592)
- **MLX issue #3860:** fp32 matmul on CUDA silently uses TF32 by default (`MLX_ENABLE_TF32`). A commenter says the M5 Metal backend follows a similar default. This is another cross-backend divergence source unrelated to FMA. (Mirror.) — [MLX issue #3860 (mirror)](https://upd.dev/ml-explore/mlx/issues/3860)
- **Taichi** exposes a global `fast_math: bool` ("Turning off the setting can prevent possible undefined math behavior"). Its docs do not describe per-backend (Metal vs CUDA) contraction handling. — [Taichi global settings](https://docs.taichi-lang.org/docs/global_settings)
- **CUDA side, for comparison:** `--use_fast_math` implies `--ftz=true --prec-div=false --prec-sqrt=false --fmad=true` ([NVIDIA forum](https://forums.developer.nvidia.com/t/how-does-use-fast-math-affect-division-precision-in-cuda/355548)). Numba-CUDA's fastmath likewise lists FTZ, approximate sqrt and div, and "contraction of multiply and add operations into single fused multiply-add operations" ([Numba CUDA fastmath](https://nvidia.github.io/numba-cuda/user/fastmath.html)). The NVIDIA floating-point whitepaper explains FMA's single rounding ([NVIDIA CUDA Floating Point whitepaper](https://www.sci.utah.edu/~beiwang/teaching/cs6210-fall-2016/NVIDIA-CUDA-Floating-Point.pdf)). NVIDIA forum guidance says `-fmad=false` disables contraction, that explicit `fma()` calls are not touched by the compiler, and that `__fadd_rn`/`__fmul_rn` block contraction ([NVIDIA forum: FMA precision issue](https://forums.developer.nvidia.com/t/fma-precision-issue/19858)).

### Inferences
- **The llama.cpp finding (2024-era) predates `mathMode`/`mathFloatingPointFunctions` (Xcode 16 / macOS 15).** On current OSes, setting `mathMode = .safe` plus `mathFloatingPointFunctions = .precise` at runtime should be equivalent to `-fno-fast-math` per the spec. Even so, it leaves contract=on, so it is not equivalent to disabling fusion.
- **A CUDA-side lever exists for blocking fusion:** `__fmul_rn`/`__fadd_rn` (or `-fmad=false`). If you control the CUDA reference build, making both sides contraction-free (or both explicitly `fma`) is far easier than reproducing ptxas's fusion choices on Metal.

- I found no PyTorch MPS, Genesis or Taichi issue specifically about FMA contraction differences versus CUDA. Searches returned only general CUDA FMA threads. This is a search gap, not evidence of absence.
- The MLX issues were read via a third-party GitHub mirror (upd.dev), and I could not confirm the original GitHub pages.
